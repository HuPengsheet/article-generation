# MLC 开源 KCoral：GPU 评测从工具变成基础设施，给 kernel agent 用的轻量 GPU 基准服务器

GPU kernel 是机器学习系统的中心，而 AI agent 正在把 kernel 开发变成一条自动化流水线：生成代码、运行、检查正确性和性能、再改进，循环往复。CAKE[1]、Kernel Design Agents[2] 等项目已经展示了这条流水线的能力。**但流水线跑起来之后，一个新的挑战浮出来：GPU 资源怎么管、怎么分**。

陈天奇团队提出 CAKE：编译器与智能体协同进化，可进化 IR 让 KDA 提速 2.05 倍

关键在于，agent 只在循环的评测环节需要 GPU。给每个 agent 独占一块卡，大量时间白白闲置；让多个 agent 共享，就必须协调，否则并发实验互相干扰计时和正确性检查，一次被污染的测量足以把搜索方向带偏。**当负载从单卡扩展到多卡、多节点，调度和管理本身也成了问题。在 kernel agent 实验和 kernel agent 强化学习这两类场景里，大量 agent 或 rollout 并发运行，这个矛盾尤其尖锐**。

2026 年 10 月 5 日，MLC 社区（Apache TVM 背后的团队）发布博客，正式介绍他们的答案：KCoral[3]，**一个轻量的基准测试服务器，把 GPU 执行从 agent 循环里解耦出来**。

agent 在自己的工作区里生成和修改代码，需要评测时把请求发给 KCoral，由它调度 GPU 访问、执行请求、把结果送回给下一轮迭代。这个项目 9 月 29 日随 TIRx Harness[4] 一同亮相，10 月 5 日有了专属博客，GitHub 仓库[5]独立开放，PyPI 包从 9 月 27 日第一个候选版到 10 月 5 日已迭代三个版本。

![图2](figure-02.png)

*图 1：KCoral 全景：agent 工作流、协议与引擎的三段式结构，左中右分别是 agent 工作流、协议层和执行引擎。agent 在自己的工作区写 kernel、改 kernel，评测请求经 HTTP 发往协议层；协议把一次实验描述为 Program 指令序列加张量、文件等数据载荷；引擎侧的 Router 与 Scheduler 把请求分配给带隔离环境的 worker，独占 GPU 执行后沿原路返回结果。值得注意协议走标准 HTTP/REST，不绑定任何编程语言，官方明确欢迎社区在协议之上自建工具和服务器。*

官方给 KCoral 列了四项能力：共享 GPU 访问，大量 agent 共用一个小 GPU 池；无缝扩展，统一入口支持单 GPU、多 GPU、多节点；可靠高效的评测，请求级隔离限制干扰，性能接近本地评测；边缘开发，agent 可以使用 NVIDIA Jetson Thor 这类远程边缘设备上的 GPU。🥱

## 一、标准化协议：远程 kernel 开发的统一接口

**本地的 agentic kernel 开发循环里，agent 生成 kernel、本地评测、修改，这条链把 agent 绑死在一块 GPU 上——GPU 难以共享，GPU 在远端时更是直接不可用。KCoral 协议就是为拆掉这个绑定设计的：本地客户端按协议向持有 GPU 的服务器发请求，服务器返回结果**。协议清晰描述 kernel、评测或调试负载，因此成为跨设备、跨 GPU 的统一接口。

协议在 HTTP 之上被设计为一个原子化的程序：一串操作序列，负责上传代码和数据、运行代码、返回结果，服务器返回指定的结果或执行错误，连同日志一起。基本操作只有四类：

官方博客给的最小例子只有十几行，原文如下：

上传一个只含 add_one 函数的 Python 模块和一个张量，在服务器 GPU 上执行加一，把结果取回来打印。**这个例子的意义在形态——客户端只是一段描述计算的程序，不碰 CUDA，不碰 GPU 驱动**。博客里顺势给了一个场景：在 NVIDIA Jetson Thor 上启动服务，在 MacBook 上开发 kernel，客户端机器连 CUDA 工具链都不用装，仓库里有现成的 Thor 示例[7]。

这套协议有两个值得展开的工程性质。

- 一是无状态：重复一个实验不需要重建上一次运行留下的隐藏状态，每段程序显式声明自己的代码与输入，worker 因此可以在实验之间随意更换。

- 二是轻量：PyPI 上的 kcoral 包运行依赖只有 numpy、ml-dtypes、httpx 三个，协议简单所以客户端简单。

## 二、KCoral 引擎：跨 GPU 与跨节点的调度

协议定义了"说什么"，引擎负责"怎么执行"。KCoral 引擎管理一台机器上的 GPU，把每个请求调度到最空闲的 GPU 上；一旦调度完成，该程序就独占这块 GPU。**独占是保证测量可信的关键设计——多个 agent 用同一块 GPU 评测 kernel，相互干扰被压到最低**。

多节点场景由 Router 承接。这是一个用 Rust 实现的组件，对外提供统一入口，按节点健康度和负载分配请求，还负责各节点 server 的生命周期管理，崩溃后自动重启。部署上有个友好的细节：节点进程主动外连 Router，节点可以藏在 NAT 后面，无需暴露入站端口。因此即使面对大量并发 agent 请求，KCoral 也能把它们摊到所管理的全部 GPU 节点上。

![图4](figure-04.png)

*图 2：KCoral 引擎架构：Router 与单节点内部结构。图左侧是多节点拓扑，Router 对外收发 HTTP，与节点间走 gRPC 传输控制与数据；右侧是单节点放大图，请求进节点后先过 Hash cache，再进 Scheduler，最后落到持有独占租约的隔离 worker。图中 Hash cache 对应一个实际的优化：评测同一 kernel 的不同实现时，脚本、张量等依赖通常完全相同、只有 kernel 不同，每次都重新上传全部文件很浪费，KCoral 按文件哈希自动跳过重复上传。*

隔离机制有两个层面。

- **文件层面用 bubblewrap：每个请求只能访问一组固定的系统目录和自己的工作目录**。选 bubblewrap 的理由官方说得很直白——**启动开销是毫秒级，而传统 Docker 容器隔离是秒级，对一次只跑几十秒的评测请求，秒级开销会直接吃掉吞吐**。隔离的动机也不只是防干扰：还要防止 agent 获取无关 agent 的信息，或者通过修改系统文件来钻奖励的空子（reward hacking）。

- **进程层面，KCoral 默认在每次程序执行后更换 worker，下一个实验拿到的永远是全新的 Python 进程和 CUDA context，跑挂的 kernel 不会把状态残留给后继者**。引擎同时支持单 GPU 与多 GPU kernel：提交多 GPU 负载时只需声明所需卡数（1 到 8），调度器会自动等待并分配足够数量的 GPU。

## 三、CPU-GPU 解耦：编译期间把 GPU 让出来

kernel 评测并不需要全程占用 GPU，尤其是编译这一步——可能很慢，却完全用不到 GPU。如果请求全程持有 GPU，编译期间这块卡就在空转。KCoral 提供两种机制防止编译占用 GPU。

## 四、KCoral CLI：远程工具，本地体验

为降低使用门槛，KCoral 提供了一套命令行接口，让常用 kernel 开发工具以与本地相同的体验运行在 KCoral 服务器上。

目前封装了 python、compute-sanitizer、ncu、run-iket、shell 五个工具，开发者或 agent 可以不做任何调用习惯的改变，就在远程 GPU 上跑正确性检查、排查内存错误、采集 Nsight Compute 报告。官方博客给的完整示例：

所有命令统一为 kcoral run TOOL [KCoral 选项] -- [原生参数] 的形式：

- -- 之前的选项选择服务器、指定要发送的文件，之后的部分原样传给 worker 上的工具。

- --send 把脚本或整个目录上传到一个全新的远程工作目录，--fetch 配合 --out 把产物（比如 profiler 报告）下载回来。

服务器地址用 KCORAL_URL 环境变量或 --host、--port 指定。每个工具的选项和指南见官方文档的 Builtin CLI Tools[9] 一节。

这套设计的受益者首先是 agent：学一套命令格式，就接通了整个 GPU 工具链。官方文档还记载了一条配套纪律——时间线、硬件报告、诊断结果都是诊断证据，正式性能比较必须用普通基准得出，因为 profiling 和插桩本身会改变执行成本，拿插桩后的数字做排名等于自我欺骗。

## 五、官方评测：保真度、吞吐与鲁棒性

KCoral 自己也被跑了分。官方博客从三个维度评估，全部在单块 NVIDIA B200 上进行。

### 5.1 保真度：保住性能反馈

kernel 优化 agent 需要可信的计时来引导方向。官方从 TIRx-kernels[10] 取了 82 个 kernel 家族的 500 组负载配置，用同一块 GPU、相同输入和相同计时设置（包括 L2 缓存冲刷），对比 KCoral 远程计时与本地直接计时，报告两者的相对偏差：

*表 2：KCoral 远程计时与本地计时的偏差。测量只覆盖 kernel 执行，不含编译、输入准备和请求延迟。超差的三组负载都是本地耗时仅 1.9 至 2.2 微秒的 RMSNorm、LayerNorm 短 kernel，绝对差只有 0.13 至 0.38 微秒——比如一个本地 2.079 微秒的 RMSNorm 负载经 KCoral 测得 2.272 微秒，0.193 微秒的差被放大成 9.28%。在亚微秒尺度上，微小绝对差就会产生大百分比差。*

### 5.2 吞吐：共享 GPU 容量

吞吐实验跑 256 个工作负载：8 个固定的 TIRx kernel 特化版本——包括 Kimi Delta Attention[11]、Alpha-MoE[12]、MiniMax 稀疏注意力[13]——各重复 32 次，每个负载从冷缓存编译、构造 GPU 输入、评测已有 kernel，不含 agent 生成时间。本地基线是不用 KCoral 顺序跑同样的负载。

并发 32 时，KCoral 达到每分钟 12.86 个工作负载，本地为 4.98，加速 2.58 倍。**更有说服力的是另一个口径：需要独占 GPU 的操作总共耗时 1190.79 秒，本地整批耗时 3083.61 秒，理论加速上限 2.59 倍——KCoral 达到了上限的 99.7%，除非压缩独占 GPU 的工作本身，几乎没有继续优化的空间**。官方另测了一个更短的负载（编译一个 4096 乘 4096 cuBLAS 矩阵乘的 C++ 封装、构造输入、检查、计时），16 个常驻 worker、16 并发下达到本地顺序吞吐的 4.86 倍。

![图6](figure-06.png)

*图 4：KCoral 吞吐评测：混合负载与矩阵乘负载实验。左图混合负载，并发从 8 提到 32，吞吐从 11.08 升到 12.86 个/分钟，曲线明显趋平——独占 GPU 的工作总量决定了上限。右图短负载，16 并发时达本地顺序的 4.86 倍；注意并发为 1 时只有 0.66 倍，远程化本身有开销，收益全部来自并发。若把 agent 生成代码的时间计入（按 KDA forward 实测轨迹的中位数，每轮约 162 秒），32 个模拟 agent 共用 16 个 worker，64 次评测 6.54 分钟跑完，朴素顺序 agent 基线估计要 180.82 分钟，全流程加速 27.63 倍。*

### 5.3 鲁棒性：失败后继续

agent 的候选程序经常失败，服务必须在失败后继续工作。官方收集了 200 个 CUDA、Triton、CuTeDSL kernel 候选（含 PTXBench[14] 评测轨迹里的候选），覆盖矩阵乘、注意力、归一化等算子，故障类型包括编译与架构拒绝、数值不匹配、运行时错误和 worker 退出。**结果：KCoral 对全部 200 个案例返回了对应的编译器、运行时或正确性检查器诊断，无一错配；每个失败案例之后再提交一个已知正常的 GPU 负载，200 次后续请求全部成功。agent 修改失败的候选再投，不需要重启服务器**。

斯坦福、CMU 与 RadixArk 提出 PTXBench：直面 GPU 底层指令，测出 LLM 内核优化的真实能力边界

这组数据在 MLC 新书的实战章节里能找到一个具象的注脚：Kimi Delta Attention 的一次优化迭代中，agent 一条命令经 KCoral 发起远程 NCU 抓取，报告里的 190464 个多余全局内存扇区指向跨步的 beta 读取；**改成 TMA 聚合加载后重新评测，加速比从 2.1528 倍推进到 2.2005 倍，第二次抓取确认多余扇区降到 6144。测量、诊断、再测量，每一步都发生在独占 GPU、全新进程和私有工作区里**。

端到端成绩方面，agent 写出的 KDA kernel 相对 FlashKDA forward 几何平均加速 2.94 倍，相对 Flash Linear Attention backward 加速 6.84 倍。

## 七、结语

KCoral 的功能列表不长：一套四操作协议、一个调度引擎、编译解耦、一套 CLI。它的意义在标记了一条分界线。

过去的 GPU 评测工具是为人设计的：人发起、人等待、人凭经验判断结果是否可信。**当发起方变成 agent——一天跑几百轮、无人值守、测量结果直接驱动下一步决策——评测就从小工具变成了基础设施，需要协议、调度、隔离和路由**。

官方评测里最值得特别的数字也许是那个 99.7%：**当环境不再添乱，工程优化的天花板就是问题本身的物理上限。KCoral 是这条分界线上第一批成型开源的样本，它回答的问题会在每一个 agent 参与性能工程的领域反复出现：当写代码的不再是人，围绕代码的那些环境，都得重新设计一遍**。
