# 数千美元、17 亿 Token、一周时间写出 Qwen 定制推理引擎，单流解码比调优后 vLLM 快 90%

Baseten 工程师受 MetaInfer 论文启发，让 Claude Code 在单张 NVIDIA B200 上为 Qwen-3.6-35B-A3B（NVFP4 精度）自主编写专用推理引擎。

Claude **以 Fable 5 驱动，自主工作约一周，消耗约 17 亿 token（绝大部分为缓存输入）和约 200 个 B200 小时，最终生成的引擎 VibeQwen 在单流解码吞吐上比调优后的 vLLM 0.25.1 快 90**%（1792 vs 943 token/s），首 token 时间（TTFT）从 28ms 降至 12ms（2.3 倍提升），并发 32 时单副本输出吞吐高 71%（10307 vs 6030 token/s）。

两个引擎目前均为实验项目，未承接生产流量，**但实验证明了"为固定部署条件让 agent 定制引擎"这条路径在成本和时间上已具备可行性**。

## 一、AI 辅助推理优化的兴起

Baseten 内部有 #ai-papers-discuss 和 #model-performance-reading-group 这样的 Slack 频道，最近一篇论文引起了我的注意：MetaInfer——一个只用技能（skills）从零构建定制推理引擎的框架，作者声称其结果在单 token 输出时间（TPOT）等常见推理指标上击败了 vLLM 这类开源最优方案。

这里的"只用技能"指不做模型后训练，也不用专门的 harness。我承认自己起初是怀疑的，但他们放出了技能工具包的仓库，**而且我们公司目前还享受着 token 不限量的好日子，于是我决定拿一个流行模型试一试，看看它到底行不行**。

结果：**在单张 B200 上以 NVFP4 精度运行 Qwen-3.6-35B-A3B，我们 LLM 生成的推理引擎在单流解码速度上比 vLLM 0.25.1（实验当时的最新版）快出最高 90%，TTFT 快 2.33 倍**，为该模型打开了此前不实用的超低延迟应用场景。

当下有几股大规模趋势正在汇聚，为 MetaInfer 这类发现和技术创造了肥沃的土壤。

![图4](figure-04.png)

*四大汇聚趋势示意图：更聪明的模型、智能体协作、可度量的优化、推理需求，最终汇成"定制推理引擎"这一结果。这张图概括了作者眼中支撑"AI 生成定制推理引擎"的四股力量——模型智能提升让长周期任务可委托、agent 协作原语（如 Goals）进入主流编码 harness、优化目标可客观度量与验证、推理需求呈复利增长带来成本压力。四者交汇，指向同一个结果：为特定部署条件定制推理引擎，从工程奢侈品变成可选项。*

模型变得更聪明，更擅长长周期任务。Anthropic 发布的 Mythos 5 和 Fable 5 是一个重要节点，标志着可放心委托给 AI 系统的任务类型向前迈进了一大步。我印象中的上一个这样的时刻是 2025 年底 Opus 4.5 的发布——从那时起，包括我在内的许多工程师，开始把 AI 编码工具从"加了香料的自动补全"转变成像 Claude Code 这样的主力工作界面。

与此同时，智能体协作的工作流和原语正在被直接打包进主流 harness，复杂的多智能体工作流变得更易上手、更易操作。其中一个重要特性是"Goals"——Claude Code 和 Codex 都提供——它能让模型围绕可度量的目标长时间工作、保持任务不跑偏。**我最早是在大约半年前 Karpathy 的 Autoresearch 项目里见到这种"实验—度量—迭代"循环的，如今它已经是编码 harness 的标准组成部分**。

![图5](figure-05.png)

*AI 推理需求增长曲线：Google 各产品界面月处理 token 量从 2024 年 5 月的 9.7 万亿增长到 2026 年 5 月的 3.2 千万亿以上，约 330 倍。这张图引自 Google I/O 2026 的公开数据，展示 Google 各产品界面月处理 token 量的增长曲线：2024 年 5 月约 9.7 万亿，2025 年 5 月约 480 万亿，2026 年 5 月已超 3.2 千万亿（quadrillion）。两年约 330 倍的复利增长，是"推理成本与性能必须持续优化"这一命题最硬的市场背景，也是 Baseten 愿意投入 agent 自动优化推理的直接动因。*

随着 AI 系统的能力不断提升，推理服务的市场需求也在增长，对成本和性能持续改进形成了巨大压力。

这些因素叠加在一起，**让"把 LLM 指向定义良好的优化问题，让它自己 grind 出解"这件事变得顺理成章**。推理性能恰好是这类自动优化的理想领域：

- 问题空间定义良好，有 TTFT、TPOT、单芯片吞吐、内存需求这些可量化的指标；

- 甚至正确性也可以对照模型的全精度参考实现做数值验证，确保性能提升不以精度为代价。

这种客观可验证性对自主优化的成功至关重要。我们还知道，**当前最优性能与光速理论上限之间存在巨大差距**。此外，推理系统极其复杂，优化搜索空间非常大——从底层的 CUDA kernel 编写，一路到动态批处理这类服务层优化。

## 二、约束解空间

LLM 可能很擅长求解定义良好的优化问题，但挑战转移到了"如何把问题框定成定义良好的优化问题"上。**你必须把约束定义清楚，谨慎选择优化目标**。agent 绝对会试图钻系统的空子来"通过"目标，所以工程师的责任是设计好游戏规则，让 agent 的成功与你的真实需求对齐。举个例子，如果你不设保持准确性的约束，你的"模型"会收敛到：

vLLM、SGLang、TensorRT-LLM 这些现有开源推理引擎，在"以商业上可接受的性能水平、服务大量模型和多种加速器"这件事上总体做得非常出色。**但通用性和易用性是有代价的：它们不会对任何一个具体的（模型 + 加速器 + 负载）组合做极致优化。MetaInfer 的前提正是：对于任何特定部署，一个高度专用（即受约束）的引擎可以跑赢这些通用引擎**。

## 三、面向生产应用改造 MetaInfer

在 MetaInfer 原论文中，**作者要求现成 agent 仅凭一份由契约（contract）和约束组成的知识库构建推理引擎，不能直接访问开源引擎的源码**。这些源码在模型训练时几乎肯定出现过，但 agent 没有文件级的直接访问权限。**agent 在工作过程中会扩展知识库，主动识别缺口，并通过结构化的实验和验证来填补**。

![图6](figure-06.png)

*针对通用大语言模型推理框架抽象层冗余、异构硬件适配成本高的问题，《MetaInfer: A Knowledge Only LLM Inference Engine Generator SKILL Toolbox》这篇文章，提出 MetaInfer——一种“LLM即编译器”的定制推理引擎生成方案。系统以契约知识库为核心，通过实现、规格评审、独立验证的多智能体分工，在不主动引用开源框架源码的约束下，根据运行时约束生成单路径专用推理引擎；同时具备知识库演化机制，可将新模型与平台信息沉淀为可复用知识。实验表明，源码参考可降低构建成本但并非必需；K100平台上生成的Qwen3-8B引擎解码性能优于vLLM；系统可通过演化完成Z200平台上Qwen3.6-27B的适配验证，为推理引擎按需生成与持续优化提供了新路径。上图是 MetaInfer 整体架构。该系统围绕CKB（Component Knowledge Base，组件知识库）构建三个循环：零参考生成循环根据用户约束生成并验证单路径推理引擎；知识库演化循环在覆盖度不足时补充新增模型或硬件平台相关知识；经验反馈循环将可复用的验证与优化经验回写到 CKB 中。*

原作者采取的实验纯粹性令人钦佩，也很有趣，但 Baseten 非常结果导向。我确实允许自己的 agent 在需要时参考开源最优方案——包括从 vLLM 和 TensorRT-LLM 里找现成的预优化 kernel，只在必要时才自己写。另外，**原论文只关注推理引擎组件本身，我把范围扩大到了完整的服务栈——最终结果对着部署在负载均衡之后的多副本服务来度量，用 AIPerf 生成负载并测量性能**。

在原论文和我的扩展中，产出都是两样东西：**推理引擎本身**，以及可**在后续运行中复用的知识库扩展**。

## 四、第一个实验：Qwen-3.6-35B-A3B 推理

### 4.1 实验设置

启动实验时，**我给 Claude Code（Fable 5）提供了论文和 MetaInfer 仓库，以及通过 SSH 访问一台 NVIDIA B200 工作站的权限。我告诉它目标硬件，并给出 Hugging Face 仓库的链接**——既包括我想用于 Qwen-3.6-35B-A3B 的 NVFP4 量化权重，也包括用作准确性 oracle 的原始全精度权重。agent 还能把候选引擎部署到 Baseten，并对部署后的端点运行 AIPerf 压测。

我们有内部的 agent 技能和 MCP 来支撑所有必需的 Baseten 交互，agent 也能访问这些。我给它设了一个 /goal：所有性能指标超过 vLLM 20%，且相对 NVFP4 基线不损失准确性。

**最终结果和所需的人工干预之少，都让我又惊又喜。Claude 在这个项目上大体自主工作了约一周，我偶尔做些方向调整——防止它过度盯住某一种流量形态，确保它关注的是生产推理性能**，而不是孤立的引擎基准测试。MetaInfer 框架用一系列不可变的门和检查点，支撑起了这种长周期的工作。

每当遇到带来准确性差异的改动，Claude 会暂停并请求我批准。最终我允许它与参考 NVFP4 实现在数值上有细微差异，只要相对 BF16 基线的整体准确性至少一样好。

### 4.2 结果

除了在小模型上早期结果令人失望、于是要求所有子 agent 都用 Fable 5 之外，我几乎没做任何 agent 协调或上下文管理。**它经历了多次自动上下文压缩，消耗了约 17 亿 token（绝大部分是缓存输入 token）和约 200 个 B200 小时。实际上它在头几天就达到了与 vLLM 持平的水平，但我为了科学，让它继续 grind 下去**。

![图7](figure-07.png)

*VibeQwen 与 vLLM 在单张 B200 上的三组正面对比：单流解码吞吐 1792 vs 943 token/s（+90%）、TTFT 12ms vs 28ms（-57%）、并发 32 单副本输出吞吐 10307 vs 6030 token/s（+71%）。这是全文最核心的一张图，三组柱状图分别对应三个关键指标：单流解码吞吐（适合推测解码的重复结构化文本）、首 token 时间（TTFT）、并发 32 时的单副本输出吞吐。注意两个口径细节：单流测试用的是"speculator-friendly"文本，收益受文本可预测性影响；图中百分比按各指标分别缩放柱长，并非同一坐标轴——跨指标比较绝对差距时要看左侧具体数字，而非柱长比例。*

最终，**这个生成的引擎——名叫 VibeQwen——在所有已测流量形态上都超过了 vLLM，某些场景下领先幅度非常大**。

- 在单张 B200 上的正面对比中，VibeQwen 在适合推测解码的单流文本（重复、结构化的内容）上达到每秒 1792 token（TPS），**而调优良好的 vLLM 部署是 943 TPS（提升 90**%）。

- 在测试语料上，它的首 token 延迟为 12ms，vLLM 是 28ms，提升 2.3 倍。并发 32 的单副本吞吐上，**VibeQwen 以 10307 输出 TPS 对 vLLM 的 6030 输出 TPS，领先 71**%。

## 五、第二个实验：用 SAM 3.1 做图像分割

第一个实验的结果太鼓舞人心了，于是我决定用 VibeQwen 实验沉淀下来的、刚刚扩充过的知识库，再试一个完全不同类型的模型。这次我要为 SAM 3.1——一个最先进的图像分割模型——做一个优化过的推理服务。

这次我以 Facebook 的参考服务器作为基线。尽管模型架构和模态完全不同，流程跑得非常顺：单张 H100 上达到每秒 91 张图，比基线提升 50% 吞吐，只用了几天时间和约 2 亿 token。

![图8](figure-08.png)

*Sammie 的提示词到掩码分割效果演示：输入图像 + 自然语言提示词（"water bottle"返回 1 个掩码、"chair"返回 2 个掩码、"person"返回 3 个掩码），输出对应物体的分割掩码与置信度。这张图展示 Sammie 的实际输出效果：左列为原始输入照片，中列为自然语言提示词，右列为分割结果。三行分别演示了"water bottle"（1 个掩码）、"chair"（2 个掩码）、"person"（3 个掩码）三种提示，输出带置信度分数（如 0.91、0.90）。作者想说明的不只是"能跑"，而是 agent 生成的服务在完全不同模态（视觉 vs 语言）和架构（SAM 3.1 vs Qwen MoE）上同样能交付可用结果——这是"知识库可跨任务复用"叙事的关键配图。*

这个名为 Sammie 的第二个实验，比最初的 VibeQwen 项目快得多、便宜得多。但由于模型架构、加速器类型都不同，且没有做对照测试，它只能提供"提示性"而非"确定性"的证据，说明知识库复用是有价值的。

## 六、走向自主推理优化

VibeQwen 和 Sammie 目前仍是实验项目，都未承接生产流量，**但相对开源最优基线的性能提升相当惊人。交付速度也相当快（以天计），人力投入很少（以小时计），成本低到很有说服力——Sammie 是数百美元量级，VibeQwen 是数千美元量级——放在企业每年在推理上花费数千万甚至数亿美元的大背景下，这个投入产出比非常划算**。在这样的规模下，哪怕个位数的百分比提升也意味着数百万美元的节省，这笔账很容易算平。

AI 在优化问题上创造价值的机会空间是巨大的，而 AI 系统自身正是这类自主优化的首要候选对象，我们已经看到了。随着推理系统效率提升、更多模型达到完成这类任务所需的智能水平，这样做的成本还会持续下降。

VibeQwen 和 Sammie 是七月底用 Fable 5 构建的，现在是十月，**开源前沿已经追得很近了——Kimi K3、GLM-5.3 等模型在许多基准上的得分已非常接近最好的闭源模型。模型智能在涨、推理成本在降、可复用知识库还在带来效率增益**——不难想象，在不太遥远的未来，这类优化会变得足够便宜、足够可靠，成为模型部署生命周期里的标准一环。
